# Outward App для Android и iOS

Дата: 7 ноября 2026 года. Основание: анализ исходников ревизии `a5b48b9`, проектного overview, `PRODUCT.md`, `DESIGN.md` и официальных материалов платформ. Статус: предложение для будущей реализации. Мобильных клиентов в репозитории пока нет; код в рамках подготовки этого плана не изменялся.

Рекомендуется сделать два нативных клиента с одной активной VPN-сессией: Android на Kotlin и Jetpack Compose, iOS на Swift и SwiftUI. Сетевой движок — встроенная библиотека sing-box/libbox. Общими должны стать правила профилей, нормализация, проверяемые контракты и тестовые примеры. Windows-приложение продолжает развиваться самостоятельно.

Пользовательский сценарий: добавить свой профиль → выбрать его → разрешить VPN → подключить устройство → видеть фактическое состояние → при необходимости сменить профиль или открыть диагностику. Собственные серверы, аккаунты, подписки и облако для этого не требуются.

Эскизы и подробные правила экранов находятся в [спецификации мобильного интерфейса](mobile-ui-spec.md). Значения стран, времени, задержки и трафика на эскизах демонстрационные.

## 1. Что означает полный TUN на мобильных устройствах

TUN — способ получить IP-пакеты устройства через виртуальный сетевой интерфейс. VLESS/Reality, Shadowsocks и WireGuard — способы передать их дальше. Поэтому режим TUN не означает отказ от существующих серверных протоколов.

Для первой версии выбирается один режим: интернет-трафик устройства направляется через выбранный профиль. Переключатель «TUN / Системный прокси» на телефоне не нужен.

Утверждение, что мобильные платформы допускают только полный туннель, слишком строгое. Android поддерживает маршруты и списки приложений; Apple также описывает маршрутизацию и Per-App VPN, но доступность последнего зависит от сценария управления устройством. Это возможное последующее расширение, а не условие первой версии. [Android VPN](https://developer.android.com/develop/connectivity/vpn), [Apple NETunnelProviderManager](https://developer.apple.com/documentation/networkextension/netunnelprovidermanager).

На iOS даже `includeAllNetworks` имеет системные исключения, например служебный трафик поддержания сети и отдельные взаимодействия с устройствами. Дополнительные исключения управляются отдельными параметрами. Поэтому интерфейс говорит «VPN для устройства», а не «100% любого трафика». [Apple includeAllNetworks](https://developer.apple.com/documentation/networkextension/nevpnprotocol/includeallnetworks).

**Полный туннель и блокировка трафика при обрыве — разные свойства.** Захват маршрутов во время работы ещё не доказывает, что после аварии ядра интернет останется заблокированным. Защита при обрыве проверяется отдельно для каждой ОС и каждого поддерживаемого режима.

## 2. Что показывает существующая кодовая база

| Проверенный участок | Полезная основа | Решение для мобильных клиентов |
|---|---|---|
| `outward_app/core/models.py`: `ConnectionProfile`, `ParsedConnection` в `connections.py` | ID, имя, страна, исходный профиль, нормализованные параметры | Сохранить смысл и совместимость импорта; выделить секреты из открытых метаданных |
| `models.py`: `SavedConnection`, `ConnectionCollection`, `RuntimeState` | Разделение профиля, сохранённого намерения и состояния сессии | Новая компактная мобильная модель без окон, портов и браузерных полей |
| `connections.py`, `vless.py` | Разбор VLESS, SS, WG; допуски к старым форматам ссылок; маскирование ошибок | Перенести правила и примеры, а не Python-рантайм |
| `singbox.py`: `build_vless_outbound`, `build_shadowsocks_outbound`, `build_wireguard_endpoint` | Конфигурация уже разделяет протоколы и использует современный WG endpoint | Общий генератор протокольной части; отдельные платформенные настройки TUN/DNS |
| `singbox.py`: `build_session_config` | Разделение bootstrap DNS и пользовательского DNS, DNS hijack, итоговый маршрут через профиль | Пересмотреть исключения и все Windows-параметры интерфейса; готовый JSON не переносить целиком |
| `sessions.py`: поколения операций, отмена, снимок профиля, восстановление | Хорошие инварианты конкурентности и состояния | Повторить в владельце мобильной VPN-сессии |
| `sessions.py`: импорты `browser`, `system_proxy`, `SingBoxManager` | Отсутствие Qt не делает модуль независимым от Windows | Не включать текущий SessionController в мобильную сборку |
| `network.py` | Проверка HTTPS отделена от TCP-задержки; есть повторные проверки готовности | Новые платформенные наблюдатели сети и доказуемая проверка через нужный outbound |
| `storage.py` | Атомарная запись и миграции | Сохранить принципы; заменить хранение сырых ссылок в JSON на защищённое хранилище |
| `traffic.py` | Учёт приращений без повторного начисления, календарный месяц | Перенести алгоритм с единственным владельцем записи и идентификатором экземпляра ядра |
| `vpn_service.py`, `vpn_pipe.py`, `vpn_client.py`, `vpn_install.py` | GUI не должен владеть временем жизни VPN | Заменить службу и named pipe на Android VpnService / iOS Packet Tunnel Extension |
| `system_proxy.py`, `browser.py`, `autostart.py`, Windows updater/packaging | Платформенный desktop-функционал | В мобильный продукт не переносить |
| `DESIGN.md`, `ui/themes.py`, `ui/i18n.py` | Graphite, две темы, RU/EN, семантические состояния | Сохранить узнаваемость; размеры, шрифты и компоненты сделать мобильными |

В репозитории закреплён sing-box **1.13.14**. Это исходная точка совместимости, а не утверждение, что версия является последней или оптимальной для нового релиза. В первом исследовательском этапе проверить её мобильную сборку, известные проблемы и необходимость согласованного обновления. Не менять движок одновременно с переносом без сравнительного набора проверок.

Windows TUN также ещё требует реальной привилегированной приёмки, что прямо отмечено в [отчёте Windows](../validation/system-vpn-and-connection-windows.md). Его генератор и тесты — источник требований, а не доказательство отсутствия утечек на телефонах.

Внутренняя альфа может начаться с VLESS/Reality, но публичная версия с заявленной совместимостью Outward должна пройти матрицу всех трёх протоколов. Если какой-то вариант не поддержан, импорт должен прямо это сообщать; нельзя сохранять профиль, который приложение заведомо не умеет использовать.

## 4. Выбор технологии

| Вариант | Что даёт | Цена и ограничения | Вывод |
|---|---|---|---|
| Kotlin/Compose + Swift/SwiftUI + общий Go/libbox | Прямой доступ к жизненному циклу VPN, привычный UI, отдельная диагностика ОС | Две UI-кодовые базы, нужны компетенции обеих платформ | Рекомендуемый путь для приложения, где VPN — основная функция |
| Flutter + нативные VPN-адаптеры | Больше общего UI | Kotlin/Swift всё равно нужны; extension не может зависеть от жизни Flutter UI; добавляется мост | Допустимо при сильной Flutter-команде, если приоритет — общий UI |
| Kotlin Multiplatform с нативным UI | Общая часть моделей и orchestration | Дополнительная связка Kotlin/Native ↔ Swift ↔ Go; libbox остаётся | Рассматривать после первых рабочих туннелей, если дублирование станет измеримой проблемой |
| Python/PySide6 на телефоне | Формальное сходство с desktop | Не решает платформенную VPN-интеграцию и усложняет сборку/ресурсы | Не выбирать |

Для libbox нужны Android AAR и Apple XCFramework. Они предусмотрены upstream-сборкой; платформенный интерфейс содержит открытие TUN, управление upstream-интерфейсом и уведомления о смене сети. Проверять API именно выбранного тега: это интеграционный интерфейс, который нельзя считать бессрочно стабильным. [Сборка libbox 1.13.14](https://github.com/SagerNet/sing-box/blob/v1.13.14/cmd/internal/build_libbox/main.go), [PlatformInterface](https://github.com/SagerNet/sing-box/blob/v1.13.14/experimental/libbox/platform.go).

Предлагаемая стартовая поддержка: Android 10/API 29 и новее, iOS 17 и новее; смартфоны в портретной ориентации — основной сценарий. Это продуктовый выбор для обсуждения на старте разработки, а не минимумы sing-box. Старые ОС добавлять только при понятной потребности. Target SDK, Xcode и SDK публикации выбрать по актуальным требованиям магазинов перед выпуском.

## 5. Границы архитектуры

| Слой | Ответственность | Кто владеет временем жизни |
|---|---|---|
| Общий контракт профиля | Распознавание формата, валидация, нормализация, версия схемы, безопасные ошибки | Библиотека без UI |
| Общая протокольная часть | Конфигурация выбранного outbound/endpoint, проверка возможностей | Библиотека рядом с libbox |
| Платформенный VPN-адаптер | TUN, DNS, upstream, исключение служебных сокетов, запуск/остановка | Android VpnService или iOS extension |
| Координатор сессии | Команды, поколения, снимок конфигурации, backoff, состояние | Сервис/extension, а не экран |
| Хранилище | Метаданные, секреты, миграции, история приращений трафика | Единственный писатель для каждой сущности |
| UI | Отображение снимка состояния и отправка команд | Activity/ViewModel либо SwiftUI App |

Предлагается небольшая общая Go-библиотека правил профилей, экспортируемая вместе с мобильной обвязкой libbox. Она не реализует криптографию протоколов и не содержит маршрутизацию ОС. На этапе прототипа проверить стоимость этого API; сложную универсальную платформу плагинов не создавать.

Windows-парсеры сейчас не переписывать. Совместимость обеспечивать общей спецификацией и набором синтетических примеров с ожидаемыми результатами. Позднее можно отдельно решить вопрос общей библиотеки для desktop, если это принесёт пользу.

Команды управления: подключить выбранную ревизию профиля, отменить, отключить, запросить фактическое состояние, запросить диагностику. События содержат ID сессии, поколение операции, ревизию профиля, этап, безопасный код ошибки и отметку времени. UI не передаёт произвольные пути, shell-команды или полный пользовательский sing-box JSON.

UI восстанавливается после закрытия, читая состояние владельца VPN. Закрытие экрана или сворачивание приложения не должно само по себе отключать туннель. Жизненный цикл принудительной остановки приложения ОС проверяется отдельно; обещание «работает после любого закрытия» не даётся.

Предлагаемое будущее размещение: `mobile/android`, `mobile/ios`, `mobile/shared`, `contracts/mobile`, `docs/validation/mobile`. В текущей задаче эти исходники не создаются.

## 6. Реализация Android

1. Kotlin-приложение содержит Compose UI, репозиторий профилей и клиент состояния VPN. Один VpnService владеет libbox и виртуальным интерфейсом; он продолжает работу независимо от Activity.
2. При нажатии «Подключить» сначала выполнить системный процесс согласия через VpnService.prepare. Отказ возвращает в неактивное состояние, сохраняя профиль.
3. Сервис своевременно переводится в foreground с уведомлением о профиле и состоянии. На актуальном target SDK указать допустимый FGS type и разрешения; не копировать случайный `dataSync` или `specialUse`. Android отдельно описывает критерии `systemExempted` для настроенных VPN-приложений. Проверить выполнение критериев на холодном старте. [VpnService](https://developer.android.com/reference/android/net/VpnService), [FGS types](https://developer.android.com/develop/background-work/services/fgs/service-types).
4. Сервис создаёт IPv4/IPv6 TUN через Builder и передаёт файловый дескриптор движку по поддерживаемому API. Владелец закрытия дескриптора должен быть определён явно, чтобы исключить двойное закрытие и утечки ресурсов.
5. Служебные соединения к серверу и bootstrap resolver защищаются от попадания обратно в VPN через protect/выбор upstream. Не применять allowBypass и не исключать из VPN всё приложение ради удобства: это может вывести пользовательские запросы UI мимо туннеля.
6. Изменения Wi‑Fi/сотовой сети отслеживаются через ConnectivityManager. События объединяются, старые DNS-ответы и подключения отбрасываются по поколению. Пропажа upstream означает ожидание сети, а не бесконечный цикл активных попыток.
7. Команды UI/сервис сериализуются; интерфейс сервиса закрыт от посторонних приложений. Выбор отдельного процесса сервиса либо одного app process зафиксировать после замеров; контракт состояния не должен зависеть от этого выбора.
8. `onRevoke`, пользовательская остановка через системные настройки и замена VPN другим приложением завершают владение. Не пытаться самовольно возвращать Outward поверх выбора пользователя.
9. Отказ в разрешении уведомлений, системная остановка приложения, battery saver, Doze и ограничения производителей входят в приёмку. Не требовать безусловного отключения энергосбережения на первом запуске.

Always-on и «Блокировать соединения без VPN» управляются системными настройками, а не фиктивным переключателем приложения. Пока cold start после перезагрузки и доступ к ключам не проверены, явно не заявлять поддержку always-on. После включения режима интерфейс должен учитывать, что соединением управляет ОС. [Android always-on VPN](https://developer.android.com/develop/connectivity/vpn).

## 7. Реализация iOS

1. SwiftUI-приложение управляет профилями и VPN-конфигурацией через NETunnelProviderManager. Обработка пакетов и libbox размещаются в отдельном target Packet Tunnel Extension, основанном на NEPacketTunnelProvider. UI не держит движок. [Apple manager](https://developer.apple.com/documentation/networkextension/netunnelprovidermanager), [Apple provider](https://developer.apple.com/documentation/networkextension/nepackettunnelprovider).
2. До UI-разработки подтвердить Network Extension entitlement, provisioning и подписание обоих targets. Для разработки и сборки потребуется Mac с Xcode; Windows-окружения текущего проекта недостаточно.
3. Общие метаданные и снимки доступны через App Group; секреты — через собственную общую Keychain access group. Не писать секреты в providerConfiguration, UserDefaults или незащищённый общий JSON. Выбрать доступность ключей с учётом работы при заблокированном экране; не добавлять обязательную биометрию к каждому reconnect.
4. Включение VPN сохраняет системную конфигурацию и проходит штатный системный диалог. Нельзя подменять его собственным макетом. Полученные от ОС состояния соединения согласуются с состоянием движка.
5. Настройка интерфейса выполняется через Network Extension API и поддерживаемый адаптер libbox. Не переносить Windows `interface_name`, поиск физических интерфейсов PowerShell или чужой приём получения дескриптора через private API.
6. Политику includeAllNetworks, DNS и системных исключений зафиксировать для минимальной и актуальной iOS. Несовместимые комбинации исключений не должны прятаться за общим переключателем «защита».
7. Смена сети, sleep/wake, перезапуск extension и возобновление UI обрабатываются без зависимости от фонового выполнения основного приложения. При каждой загрузке UI перечитать системные конфигурации и состояние; не сохранять зелёный статус как факт.
8. Память extension — отдельный бюджет: измерять steady state, пики reconnect, UDP и число потоков. Не брать «50 МБ» как универсальную гарантию для всех ОС и устройств; Apple DTS рекомендует проверять конкретные комбинации. [Обсуждение Apple DTS](https://developer.apple.com/forums/thread/73148).
9. On-demand подключение добавлять после испытаний правил, ручной остановки и холодного старта. Оно не равно управляемому Always On VPN: корпоративный always-on Apple описывает для соответствующего управления устройствами. [Apple routing](https://developer.apple.com/documentation/networkextension/routing-your-vpn-network-traffic).

Сборка в симуляторе проверяет интерфейс и часть контрактов; приемка реального VPN, фоновой работы и сетевых переходов проводится на физических iPhone.

## 8. Контракт профиля и совместимость

Метаданные: стабильный ID, название, страна, протокол, сервер, порт, ревизия, даты создания/изменения/последнего использования. Секреты: UUID VLESS, пароли SS, private/preshared keys WireGuard и исходная конфигурация, если она содержит эти значения. В открытом хранилище остаётся ссылка на защищённую запись.

Настройки мобильного клиента: выбранный ID профиля, DNS-политика, язык, тема, политика восстановления, версия схемы. Текущее состояние содержит активный ID и ревизию профиля отдельно от выбранного для следующего запуска, ID экземпляра движка, монотонное начало сессии, состояние ОС/ядра/проверки связи и безопасную последнюю ошибку.

| Протокол | Что подтверждено исходниками Windows | Граница первой мобильной версии |
|---|---|---|
| VLESS | Парсер требует UUID, сервер/порт и Reality public key; генератор включает Reality/uTLS, SNI, short_id и optional flow | VLESS/Reality в реально проверенных вариантах; не обещать произвольные WS/gRPC/XHTTP/TLS-ссылки, которые текущий генератор не воспроизводит |
| Shadowsocks | SIP002-подобные ссылки, legacy base64, параметры plugin/network передаются генератору | Базовые шифры из согласованной матрицы; плагины только после проверки в мобильной сборке. Наличие поля в парсере не доказывает работу внешнего plugin |
| WireGuard | Один Interface/Peer по текущей модели, адреса, DNS, MTU, AllowedIPs, preshared key, keepalive; endpoint вместо старого outbound | Один peer на старте, UDP и IPv4/IPv6 по проверенной матрице; многопировые конфиги не сводить молча к последнему peer |

Особый случай WG: узкий AllowedIPs не гарантирует доступ ко всему интернету. Импорт распознаёт такой профиль и объясняет несовместимость с выбранной full-tunnel-моделью. Нельзя молча расширять AllowedIPs или отправлять остальное напрямую. Продуктовое правило первой версии — не подключать такой профиль как полный интернет-VPN; поддержка частных сетей потребует отдельного режима.

Неподдержанные transport, plugin, обязательные поля и версии схемы дают конкретную ошибку до запуска. Профили не получают новые значения, которые меняют смысл подключения, без явного решения пользователя.

## 9. Импорт и перенос с Windows

Импорт выполняется локально. Источники: вставка по явному нажатию, камера QR, системный выбор файла `.conf`/текстового профиля. Буфер обмена не читается в фоне. Камера запрашивается только при сканировании; отказ оставляет вставку и файлы доступными.

Последовательность: ограничение размера → распознавание → разбор → проверка совместимости → предварительный просмотр имени/страны/протокола → сохранение секрета и метаданных одной согласованной операцией. Импорт ничего не подключает автоматически и не открывает внешние URL.

Перед переносом правил подготовить обезличенный набор примеров: нормальные и исправляемые VLESS-ссылки, bracketed IPv6, percent encoding, варианты base64 SS, пустые/повреждённые ключи, разные регистры и повторные секции WG, неподдержанные plugins/transports, слишком длинный QR. Ожидаемое поведение фиксируется для каждого примера.

Дубликаты определяются по нормализованной конфигурации локально. Пользователь получает выбор сохранить копию или заменить; совпадение имени не означает идентичность сервера. При конфликте ID импортированному профилю можно назначить новый ID, сохранив связь импорта в метаданных.

Из Windows в первой версии переносятся отдельные исходные ссылки и WG-конфигурации. Сырые файлы `profiles.json` сейчас содержат секреты, а `settings.json`/`connections.json` — Windows-поля; их нельзя считать готовым мобильным форматом. Удобный защищённый массовый экспорт desktop — самостоятельная последующая задача. Для первоначального импорта не нужен сервер синхронизации.

## 10. Сетевая политика и проверка готовности

1. **Маршруты.** По умолчанию интернет IPv4 и IPv6 направляется в туннель. Локальные подсети из Windows автоматически не исключаются. Исключение служебных сокетов движка задаётся платформенным адаптером и не распространяется на произвольные пользовательские запросы.
2. **IPv6.** Если профиль/сервер не поддерживает семейство, нельзя оставлять его незаметно на прямом маршруте. Выбрать и проверить блокировку неподдержанного семейства или отклонение подключения с объяснением.
3. **DNS.** Пользовательский DNS после установления сессии идёт через выбранный outbound. Bootstrap-разрешение имени самого сервера отделяется: минимально необходимый запрос до туннеля, с документированной политикой. Не делать прямой fallback пользовательского DNS при ошибке.
4. **IPv6-only/NAT64.** Не копировать жёсткую зависимость от IPv4-адреса bootstrap resolver `1.1.1.1`. Сначала проверить достижимый resolver и разрешение endpoint на IPv6-only сети; учесть DNS64 и IPv4 literals.
5. **Готовность.** Нужны успешная настройка TUN/DNS ОС, работающий движок и TLS-проверка через нужную сессию. На iOS запрос из containing app не следует считать достаточным доказательством: он может идти другим системным путём. Предпочтителен запрос через контролируемый outbound движка с отдельной проверкой захвата трафика внешнего приложения.
6. **Контрольные адреса.** В Windows используются gstatic и Cloudflare. На мобильном зафиксировать два независимых контрольных адреса, TLS и ожидаемый ответ. Один недоступный сайт не должен немедленно разрывать здоровый VPN. Такие запросы являются внешними обращениями и должны быть отражены в описании приватности; секреты профиля к ним не отправляются.
7. **Задержка.** В первой версии использовать единое название «Проверка связи»: длительность HTTPS через туннель, включая её собственные этапы. Не называть её ICMP ping или TCP-задержкой сервера. Прямой TCP ping из desktop не переносится как постоянная мобильная проверка; WG остаётся UDP-протоколом.
8. **MTU/UDP.** Подобрать MTU по измерениям; проверить QUIC, UDP DNS, видеосвязь, крупные передачи и проблемные сотовые сети. Одно успешное открытие веб-страницы не закрывает этот пункт.

## 11. Состояния и правила управления

| Состояние | Что видит пользователь | Доступное действие |
|---|---|---|
| Нет профиля | «Добавьте профиль» | Добавить; подключение недоступно |
| Отключено | Выбранный профиль, «Не подключено» | Подключить, выбрать/редактировать профиль |
| Ожидание разрешения | Объяснение и системный диалог | Разрешить/отказать; отказ не считается сетевой ошибкой |
| Подготовка/подключение | Текст этапа, нейтральная индикация | Отменить; повторный старт не создаёт новую сессию |
| Подключено | Фактический активный профиль, время, связь, трафик | Отключить; выбрать другой профиль с подтверждением переключения |
| Нет сети | «Ожидание сети» | Отменить ожидание; не крутить частые retries |
| Связь не подтверждена | «VPN активен · связь не проверена» | Повторить проверку, открыть журнал, отключить |
| Восстановление | Причина и следующая попытка | Отменить/отключить |
| Остановка | «Отключение…» | Дождаться очистки; дубликаты команд игнорируются |
| Ошибка | Проблема и действие исправления | Повторить, выбрать профиль, журнал |
| VPN отозван/заменён | «VPN отключён в настройках устройства» | Новый старт только по допустимому намерению пользователя |

Connected означает: ОС держит наш VPN, движок работает, начальная проверка маршрута завершилась успешно. При последующей потере подтверждения связи не показывать прежнее безусловное зелёное состояние. Ошибка одной проверки переводит в уточнение состояния; повторные неуспехи запускают ограниченное восстановление. Потеря самого VPN/движка обрабатывается сразу.

Предлагаемые стартовые параметры, которые затем уточняются измерениями: бюджет первичного подключения до 20 секунд; не более трёх активных повторов с задержками порядка 1/3/10 секунд и jitter; после исчерпания — явная ошибка. При отсутствии сети попытки приостанавливаются до события её появления. Успешный reconnect и ручной новый запуск сбрасывают серию. Долгоживущие режимы always-on/on-demand получают отдельную политику.

Ручная остановка отменяет текущие и отложенные попытки. Поздние callbacks не восстанавливают выключенную сессию. Таймер длительности берётся из монотонных часов владельца сессии; перезагрузка создаёт новую сессию.

При смене активного профиля показать: «Переключиться на …? Текущее соединение прервётся». После подтверждения: остановить прежнюю сессию → очистить ресурсы → запустить снимок новой ревизии → проверить готовность. Мгновенная бесшовная смена не обещается. В промежутке политика пропуска/блокировки соответствует реально включённому системному режиму; предупреждение не должно обещать блокировку, если она не обеспечена.

Редактирование активного профиля сохраняет новую ревизию для следующего старта и предлагает применить через переподключение. Текущая сессия продолжает показывать свой снимок. Удаление активного профиля сначала требует остановки; нельзя оставлять работающий VPN с удалёнными секретами и потерянным владельцем.

## 12. Защита при обрыве и автоматическое подключение

| Свойство | Android | iOS |
|---|---|---|
| Восстановление внутри работающего VPN | Координатор сервиса | Координатор extension |
| Запуск без открытого UI | Системный VpnService при выполнении условий | Системный запуск extension при выполнении правил |
| Постоянный системный режим | Always-on в настройках после отдельной приёмки | On-demand отдельно; управляемый Always On не является эквивалентом обычного переключателя приложения |
| Блокировка без VPN | Системный lockdown после отдельной приёмки | Сочетание Network Extension-политик требует тестов; не обещать одинаковый с Android kill switch |
| После ручной остановки | Не восстанавливать по устаревшей команде; учесть системное управление | Согласовать отключение on-demand с ручной остановкой |
| После reboot до разблокировки | Проверить доступность ключей; при невозможности не заявлять поддержку | Проверить Keychain и системные условия; не обещать pre-unlock доступ без испытаний |

Первая публичная версия может выпускаться без отдельного kill switch, если это прямо отражено в интерфейсе и описании. Если обязательным требованием станет отсутствие обхода при аварии, соответствующая платформенная матрица превращается в блокирующее условие выпуска, а не пункт «позже».

## 13. Хранение, приватность и диагностика

- Android: метаданные в локальной БД, настройки в штатном хранилище; секреты шифруются ключом из Android Keystore. Проверить поведение восстановления backup, удаления ключей и блокировки устройства.
- iOS: метаданные в контейнере приложения/App Group; секреты в собственной Keychain group с доступом extension. Политику доступности и возможное сохранение записей после удаления приложения проверить явно.
- Секреты и сырые профили исключаются из обычных резервных копий и журналов. Временный импорт/экспорт не должен оставлять постоянные незащищённые копии в app cache.
- Журнал ограничивается по объёму и сроку хранения. В обычном режиме не хранить содержимое пакетов, посещённые домены и подробные destination IP. Debug — явное действие с ограниченным сроком; перед экспортом проверять очистку.
- Маскирование применяется к URL, UUID, SS password, private/preshared keys, фрагментам JSON/INI и сообщениям движка. Переносится не только regex desktop: нужны проверки новых форматов ошибок.
- Экран диагностики показывает версию приложения и ядра, этап/код ошибки, время, тип сети и обезличенное состояние DNS/маршрутов. Профильные секреты для поддержки не нужны.
- Экспорт журнала выполняется через системный share sheet по действию пользователя с предварительным просмотром. Ничего не отправляется автоматически.
- Без аналитических SDK и удалённого crash upload по умолчанию. Если они появятся, это отдельное решение с проверкой содержимого и правилами магазинов.

Шифрование локального профиля защищает данные в хранилище, но не является обещанием защиты от полностью скомпрометированного устройства.

## 14. Статистика и расход батареи

За месяц показывается сумма upload+download, замеченная Outward; это не счёт оператора и не трафик всех приложений за время до установки. Правило периода: календарный месяц в локальной зоне на момент учёта; смена зоны/часов не должна повторно начислять старые байты. Граница месяца имеет точность интервала выборки.

Каждый экземпляр движка имеет отдельный source ID. Хранилище сохраняет последний cumulative counter и начисляет только дельты. Падение счётчика означает новый источник, а не отрицательный трафик. Финальная запись при остановке и периодические checkpoints не удваивают значения. После аварии допустимая потеря ограничена интервалом checkpoint и должна быть измерена.

UI обновляет показатели примерно раз в секунду только при видимом экране. Фоновый сервис не будит UI ради счётчика. Предлагаемый checkpoint — 30–60 секунд и при остановке; запись каждую секунду на диск не нужна. Использовать штатный API статистики движка; дополнительный публичный HTTP API ради метрик не открывать.

Проверку связи выполнять при старте, смене сети, возврате на главный экран и вручную; фоновую частоту подобрать измерениями, а не копировать Windows polling каждые пять секунд. Ошибка метрик не должна отключать VPN или запускать reconnect.

Суммарно: примерно **59–90 человеко-дней** до релиз-кандидата базового объёма. При двух мобильных разработчиках и частичной поддержке QA ориентир планирования — **9–13 календарных недель после M0**, с учётом зависимых этапов и исправлений. Один разработчик двух платформ — ориентировочно **14–20 недель**. После M1 оценку пересчитать по реальным затратам на libbox и ограничениям iOS. Always-on, on-demand, split tunneling и защищённый массовый экспорт в эту базовую оценку не включены.

Не выполнять Android полностью и только потом впервые пробовать iOS: именно iOS extension и лицензирование могут изменить фундаментальные решения. В M1 обе платформы получают рабочий минимальный туннель; затем продуктовые экраны можно делать параллельно.

## 17. Матрица проверки

| Область | Обязательные сценарии | Доказательство приёмки |
|---|---|---|

| Маршруты/DNS | IPv4-only, dual stack, IPv6-only/NAT64; A/AAAA, системный DNS, пользовательский DoH | Контроль внешних IPv4/IPv6 и DNS с захватом на контролируемой сети/сервере |
| Защита при отказах | Убийство ядра/extension, ошибка TUN, падение resolver, недоступный endpoint | Зафиксировано, когда трафик блокируется и когда ОС возвращает прямой маршрут; UI отражает факт |
| Сеть | Wi‑Fi↔LTE/5G, airplane mode, потеря сигнала, captive portal, metered network | Нет циклических reconnect и зависшего зелёного статуса; отмена работает |
| Жизненный цикл | Фон, экран заблокирован, sleep/wake, UI process death, reboot, force-stop | Реальное состояние восстановлено; поведение после force-stop описано отдельно |
| Разрешения | Отказ/отзыв VPN, отказ камеры/уведомлений, другая VPN-программа | Нет самовольного возврата VPN; остальные способы импорта доступны |
| Конкурентность | Быстрые нажатия, отмена на каждом этапе, профиль изменён/удалён, поздний callback | Не более одной сессии и одного актуального запуска; ресурсы освобождены |
| Секреты | Ошибочные URL/JSON/INI, debug/export, backup/restore, скриншоты диагностики | В артефактах нет ключей, UUID и паролей |

| Интерфейс | RU/EN, длинные имена, светлая/тёмная тема, крупный текст, TalkBack/VoiceOver, клавиатура | Основные действия доступны без обрезания и только цветового кодирования |
| Обновление | Чистая установка, upgrade со старой схемы, неизвестная версия схемы, миграция при ошибке | Данные сохраняются; неподдержанная схема не перезаписывается |
| Ресурсы | 8 часов туннеля с выключенным экраном, 30 минут активной нагрузки, серия из 100 connect/disconnect | Нет crash/ANR, роста FD/goroutine/памяти; измерены overhead батареи и пиковая память |

Минимальный парк: Android на минимальной и актуальной поддерживаемой ОС, хотя бы Pixel и устройство с ограничениями фоновой работы другого производителя; iPhone на минимальной и актуальной поддерживаемой iOS, включая менее мощную модель. Эмуляторы расширяют UI-охват, но не заменяют эти устройства.

Численные бюджеты cold/warm connect, памяти и battery overhead установить после M1 как измеренные лимиты с запасом; до этого не обещать проценты расхода батареи. Сравнивать одинаковые условия с прямой сетью и официальным клиентом sing-box на той же версии ядра.

## 18. Решения перед первой задачей разработки

| Вопрос | Предлагаемое решение | Когда окончательно зафиксировать |
|---|---|---|
| Нужны ли окна/локальные прокси? | Нет, одна VPN-сессия | Принятие продуктового объёма |
| Нативный UI или Flutter? | Два нативных UI, общая протокольная часть | До M1 |
| Лицензия встроенной сборки | Согласовать разрешённую схему с правообладателями | M0, блокер |
| Каналы и аккаунт Apple | Планировать организационный аккаунт и App Store; подтвердить применимость требований | M0, блокер публикации |
| Минимальные ОС | Android 10+, iOS 17+ | M0 по аудитории и парку |
| Версия ядра | Исследовать закреплённую 1.13.14, затем выбрать проверенный pin | M1 |
| Полный интернет-VPN для узких WG AllowedIPs | Отклонять как несовместимый с режимом | M2 |
| Защита при обрыве — обязательство v1? | Базовый v1 без универсального обещания; усиленный режим отдельно | До окончательного определения release gates |
| Массовая миграция из Windows | После v1; сначала ссылки/QR/конфиги | Продуктовый backlog |

Эскизы и этот план не являются уже согласованным дизайном или результатом испытаний мобильного VPN. Они достаточно определяют следующий шаг: закрыть M0 и затем проверить два минимальных настоящих туннеля в M1, прежде чем разворачивать всю UI-разработку.
